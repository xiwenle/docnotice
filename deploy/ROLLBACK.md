# 回滚说明（2026-11-11 管理员批量治理版）

> 适用版本标签：`admin-bulk-governance-v1.1`
> 回退基线标签：`admin-bulk-baseline-20261111`  
> 本轮没有数据库结构变更、没有迁移；回退代码不要求回退数据库。

## 1. 什么时候需要回滚

出现以下任一情况时，先停止继续写入并评估回滚：

- 服务无法启动，或 `/health` 持续异常；
- 登录、资料列表、通知列表等核心入口不可用；
- 批量操作导致数据异常，且无法在应用内安全纠正；
- 恢复备份后应用无法继续正常工作。

只影响单个页面的样式或文案问题时，优先做小范围修复，不要直接回滚全部业务版本。

## 2. 回滚前必须做的事

1. 停止应用服务，避免边恢复边写入。
2. 把当前 `data/` 整个目录复制到独立位置留档；不要覆盖原目录。
3. 保留当前 `.env` 和部署配置，不要用回滚包覆盖生产密钥。
4. 记录当前版本、回滚原因、操作人和时间。
5. 如果本次问题涉及数据库损坏，不要先手工改库；使用应用现有备份恢复流程或由运维按备份清单处理。

## 3. 代码回滚

选择以下一种方式：

- 使用发布仓库：检出或重新部署 `admin-bulk-governance-v1` 或 `admin-bulk-baseline-20261111` 对应的代码；
- 使用发布包：按 `release/` 中保留的已验证 ZIP 或 Git 标签重建部署包，不要依赖本地临时目录。

不要直接删除当前目录后再手工拼文件。新代码目录准备好并通过 `python scripts/check_env.py` 后，再切换启动路径。

## 4. 数据是否需要恢复

- 仅代码/接口回归：通常只回退代码，保留当前 `data/`。
- 批量操作写错数据：先确认能否用批量恢复、单条恢复或应用备份纠正；不要直接编辑 SQLite。
- 数据库或文件同时损坏：停止服务，使用最近的完整备份恢复；恢复前必须保留当前数据副本。

## 5. 回滚后验证

至少完成：

1. `/health` 返回 200；
2. `admin_demo` 能登录，工作台可打开；
3. 资料列表和资料详情可打开，文件可下载；
4. 通知列表和通知详情可打开；
5. 备份列表可打开，最近备份可见；
6. 浏览器控制台无新增 error，关键接口无 4xx/5xx（预期鉴权 401 除外）。

## 6. 已知边界

- 批量预览 token 和恢复维护闸门当前是进程内状态，部署仍按单进程运行；不要直接扩成多 worker。
- 本轮无数据库迁移，但这不代表可以跳过数据留档；任何回滚前都必须先复制当前 `data/`。
- 不要为了回滚方便关闭后端权限校验或文件安全检查。
